# Аудит усреднения температурных профилей в Streamlit-дашборде

Дата аудита: 2026-08-20  
Файл дашборда: `scripts/profile_dashboard.py`  
Старая функция: `month_mean()` (строки ~462–502 до рефакторинга)

## 1. Какие строки данных использовались

- Брались **включённые** наблюдения (`enabled`) из списка **видимых** профилей текущего календарного месяца (`visible`), уже отфильтрованных по сроку, дням, инверсии и т.д.
- Для каждого наблюдения вызывались `observation_plot_arrays()` → `prepare_plot_arrays()` или `raw_plot_arrays()` — те же массивы, что и для отрисовки кривых на графике.
- Использовались пары `(y, t)` где `t` — температура, `y` — давление (гПа) или высота (м) в зависимости от выбранной вертикальной оси.
- Профили **без уровней** или с `< 2` точек после подготовки **не участвовали**.

## 2. Как сопоставлялись уровни разных радиозондов

- **Не по физическому давлению/высоте напрямую**, а через **общую искусственную сетку из 40 точек** `np.linspace` между min и max Y **по объединённому диапазону** всех включённых профилей.
- Для давления: `grid = linspace(y_hi, y_lo, 40)` (от максимального к минимальному P).
- Для каждого профиля: сортировка `(y, t)` по `y`, затем `np.interp(grid, y_sorted, t_sorted)`.
- **Не использовалась** фиксированная проектная сетка 500–925 гПа с шагом 25.

## 3. Была ли интерполяция

- **Да**, линейная `numpy.interp` на динамической сетке.
- **Экстраполяция отключена** (`left=np.nan`, `right=np.nan`) — за пределами диапазона профиля NaN.

## 4. Давление или высота

- Зависело от переключателя «Вертикальная ось» в сайдбаре.
- По умолчанию — **давление**; при переключении на высоту интерполяция шла по **height_m** из тех же уровней (порядок по давлению).

## 5. Обработка пропусков

- NaN после интерполяции **не заменялись нулём**.
- На каждом уровне сетки: `np.nanmean` по профилям с ненулевым числом валидных значений.
- Уровни без данных оставались NaN.

## 6. Вес каждого профиля

- **Каждый включённый профиль имел вес 1** на каждом уровне, где интерполяция дала число.
- Год с большим числом запусков автоматически получал **больший суммарный вес** (неявно, без предупреждения в UI).

## 7. Вес каждого года

- **Не нормализовался.** Все профили всех лет в выборке усреднялись вместе.
- Это соответствует будущему **методу A**, но **не было подписано** в интерфейсе.

## 8. Усреднение по индексам строк

- **Напрямую по индексам CSV/JSON — нет** (использовалась интерполяция).
- **Но**: динамическая сетка `linspace` менялась при изменении состава профилей → координаты «средней» линии **не были стабильными** между сессиями.
- При смене оси Y с P на H сетка строилась по **другой физической координате** — сравнение «month mean» между режимами было неоднозначным.

## Почему «month mean» был неоднозначен

1. Название предполагало «среднее за календарный месяц как климатологию», но расчёт был **profile-weighted mean** без явной формулы.
2. Не было выбора **метода B** (равный вес годам).
3. Не было фиксированной вертикальной сетки.
4. Не было фильтра `(year, month)` для исключения отдельных месяцев лет.
5. Не показывались метаданные: N профилей, N лет, метод, интерполяция.

## Новая реализация (после рефакторинга)

- Общая интерполяция: `gdex_bufr/profile_climate/profile_interpolation.py` → `interpolate_temperature_profile()`.
- Усреднение: `gdex_bufr/profile_climate/profile_averaging.py` → `compute_profile_average()`.
- UI: вкладка **«Климатологическое усреднение»** + блок сайдбара «Усреднение температурных профилей» (`scripts/dashboard_climatology.py`).
- Сетка давления по умолчанию: **500–925 гПа, шаг 25** (как в `article_figures_config.yaml`).
- Сетка высоты AGL: **0–5000 м, шаг 100**.
- `obs_qc.interp_on_pressure_grid` делегирует в общую функцию.

### Method A

\[
T_A(q) = \frac{\sum_i w_i(q)\, T_i(q)}{\sum_i w_i(q)}, \quad w_i(q)=1 \text{ если } T_i(q) \text{ существует}
\]

### Method B

1. \(T_{y,m}(q) = \mathrm{mean}_{i \in (y,m)} T_i(q)\)
2. \(T_B(q) = \mathrm{mean}_y T_{y,m}(q)\) — каждый year-month mean весит 1.

Q25/Q75 для A — по индивидуальным профилям; для B — по year-month mean profiles.
